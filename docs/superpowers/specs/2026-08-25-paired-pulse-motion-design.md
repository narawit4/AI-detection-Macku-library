# Paired-Pulse Motion Design

## Goal

Replace Jitter's existing general two-dimensional motion generator with a
minimal vertical paired-pulse engine. While the configured Trigger and
optional Modifier are held, the engine alternates equal upward and downward
relative Makcu movements around the starting position. Complete pulse pairs
have zero intended displacement and do not accumulate directional drift.

This behavior can reduce net movement generated by Jitter itself. It does not
promise target stabilization in every application because sensitivity, input
filtering, frame rate, and relative-input handling belong to the consuming
software.

## Motion Model

One pair contains two half-pulses of equal magnitude:

1. pair A sends `up`, then `down`;
2. pair B sends `down`, then `up`;
3. subsequent pairs repeat A, B, A, B.

Alternating which direction starts each pair prevents repeated short runs from
always favoring one direction. Horizontal output is always zero. Screen
coordinates remain in use, so negative Y is upward and positive Y is downward.

The half-pulse interval is `1 / (pulse_rate_hz * 2)`. The engine emits no more
than one current half-pulse per worker iteration. If scheduling falls behind,
obsolete half-pulses are discarded instead of replayed, so movement never
builds a backlog.

`Smooth` ramping scales pulse magnitude from zero to the requested size during
the first 150 ms. The magnitude is sampled once at the start of each pair and
reused for its opposite half, so ramp growth cannot create pair drift. An
unsigned fractional magnitude accumulator chooses the integer size for a whole
pair and preserves sub-pixel ramp output without directional bias. `Instant`
uses the requested pulse size immediately. Every emitted axis is clamped to the
configured pulse size and to the Makcu-safe integer range.
No separate acceleration, waveform, randomization, angle, or horizontal-motion
system remains.

STOP, disconnect, hotkey disable, Trigger release, and shutdown signal the
existing cancellation event immediately. Cancellation never waits for the
second half of a pair and never sends a compensating movement after stop. This
keeps emergency stop authoritative; a run interrupted between half-pulses may
therefore end one pulse away from its starting point.

## Settings and Presets

`MotionSettings` becomes an immutable three-field snapshot:

- `pulse_size_px`: floating-point, range 1-8 px, default 2 px;
- `pulse_rate_hz`: floating-point, range 10-60 complete pairs per second,
  default 30 Hz;
- `ramp_mode`: `Instant` or `Smooth`, default `Smooth`.

The three presets are:

| Preset | Pulse Size | Pulse Rate | Ramp |
| --- | ---: | ---: | --- |
| Soft | 1 px | 20 Hz | Smooth |
| Balanced | 2 px | 30 Hz | Smooth |
| Strong | 4 px | 45 Hz | Instant |

`Custom` remains display-only and represents any current combination that does
not exactly match a preset.

## Configuration Migration

The configuration schema advances from version 1 to version 2. Version 2 saves
only the three new motion keys and never persists phase, fractional remainder,
held-button state, Moving state, or jitter-enabled state.

When loading schema version 1, the application preserves unrelated supported
values such as Trigger, Modifier, hotkey, and theme, but replaces the obsolete
motion document with the new safe defaults. The migrated document is written
only through the normal atomic save path; loading alone does not overwrite it.
Malformed version 2 values are clamped or replaced with safe defaults. A schema
newer than version 2 remains untouched and continues to disable saving, matching
the existing forward-compatibility rule.

## Interface

The Control page keeps connection state, Trigger, Modifier, Enable, STOP,
Test 3s, reconnect, theme, and hotkey behavior.

The Motion page contains:

- the `Soft`, `Balanced`, `Strong`, and `Custom` preset selector;
- a slider plus exact-value input for Pulse Size;
- a slider plus exact-value input for Pulse Rate;
- one Ramp selector with `Instant` and `Smooth`;
- a concise live summary, for example `2 px paired pulse at 30 Hz | Smooth`.

All obsolete numeric controls and waveform/curve selectors are removed. Since
no advanced motion settings remain, the Advanced navigation destination and its
scrolling page are removed rather than retained empty. The fixed outer geometry,
persistent runtime dock, visible STOP button, theme, and Consolas typography do
not change.

## Runtime Integration

The pure engine remains in `motion.py` and has no Tkinter or Makcu dependency.
It owns only pair phase, next due half-pulse, ramp progress, and fractional Y
remainder. A fresh engine or explicit reset starts a new A pair.

`makcu_service.py` continues to own the daemon movement worker, cancellation,
generation checks, device movement, duration handling, and error containment.
It requests immutable settings snapshots under the existing short lock and
sends the engine's integer `(0, dy)` output through the supported Makcu move
call. Test 3s uses exactly this production path while bypassing Trigger as it
does today.

## Testing

Hardware-free tests cover:

- exact `up/down`, then `down/up` pair ordering;
- zero horizontal output and zero net output for every complete pair;
- no long-term drift across many complete pairs;
- fractional accumulation during Smooth ramping;
- rate timing and discard-not-backlog behavior after a delayed step;
- immediate reset and cancellation between half-pulses;
- settings defaults, validation, clamping, immutability, presets, and round trip;
- schema 1 migration, schema 2 round trip, malformed values, atomic saves, and
  unsupported future-schema protection;
- the reduced Motion UI, summary, preset selection, fixed geometry, persistent
  STOP, Trigger/Modifier behavior, Test 3s, hotkey, and shutdown.

The standard compile, complete unit suite, and `import makcu` verification remain
required. Hardware verification additionally checks pair direction and rate,
Trigger/Modifier gating, reconnect, Test 3s, STOP between half-pulses, hotkey
disable, disconnect, and shutdown with a connected Makcu device.
